# ACP Session Bridge v0.4.0 需求范围：可靠续聊与会话管理

**【冻结定稿】2026-11-27** · 基线：[v0.3.1](https://github.com/ummmme/acp-session-bridge/releases/tag/v0.3.1)（[`9837730`](https://github.com/ummmme/acp-session-bridge/commit/9837730)）

**核心目标：昨天在同一个 Claude Code 对话里先用 Gemini 会话 A 评审方案，再切到 B 讨论测试。今天用 `claude --resume` 恢复原对话，回到原项目直接输入 `/gemini 上次还缺哪个测试？`，回答问题的仍是 B。** 正常续聊无需先查状态、手动恢复或重述背景。

v0.3.1 已支持活会话续聊、A/B 切换、按下游会话 ID 尝试恢复，以及子进程退出后的诊断。v0.4.0 的 **P0** 是让普通追问在桥接器重启后也能找对讨论、核准模型、只发送一次；**P1** 是会话命名和只读状态查询。用户即使从不给会话起名，P0 也应独立通过验收。

## 1. 会话归属与默认行为

以 **Claude 对话标识 + 项目真实根目录** 划分作用域。每个作用域可以有多个 Gemini 会话，同时最多有一个当前会话。书签区分两个路径：
- `projectRoot`（查找书签的项目根目录）：由桥接服务对传入的 `cwd` 先求 `realCwd = realpath(cwd)`，再向上做纯文件系统探测（不启动 `git` 子进程），取**最内层包含 `.git`（含普通仓库 `.git/` 目录与独立 `git worktree` 的 `.git` 文件）或项目级 `.acp-mcp.json`（明确排除用户级 `~/.acp-mcp.json`）的目录**；同一 worktree 下的任意子目录收敛到同一 `projectRoot`，不同 `git worktree` 各自独立。无上述项目标记的非 Git 项目，优先使用宿主明确提供的项目根（如 Skill 传入的 `${CLAUDE_PROJECT_DIR}` / 显式 `projectRoot`），否则按启动目录 `realCwd` 隔离（只有用户级 `~/.acp-mcp.json` 时，`~/项目甲` 与 `~/项目乙` 绝不归属到 `$HOME` 共用书签）。
- `sessionCwd`（创建该下游会话时使用的真实工作目录）：仅在 `start_session` 首次创建会话时锁定为当时的 `realCwd`。后续无论用户从根目录还是任意子目录触发追问或恢复，一律按 `projectRoot` 定位书签，并**强制使用书签中持久化的原 `sessionCwd`** 启动子进程、计算 `acpSessionKey` 及调用下游 `session/load`。

| 用户操作 | 预期行为 |
| --- | --- |
| 首次在该作用域输入 `/gemini <问题>` | 没有历史记录时创建 A 并设为当前。下一条普通提问继续发给 A。 |
| 同一对话里换话题、进入项目子目录或隔天追问 | 沿用当前会话。 |
| `/gemini new [问题]` | 创建独立的 B，保留 A。B 创建且配置核实成功后才切换当前指针；省略问题时不发送业务提问。 |
| `/gemini use A` | 找到或恢复 A 后切换；失败时保留原指针。切换本身不发送提问。 |
| 正常退出 Claude Code，次日 `claude --resume` | 宿主退出标记为离线，保留原记录与指针；最后使用的是 B，回来时优先接回 B。若退出时仍有未结算任务，先检查该轮状态。 |
| `/gemini close A` | 用户显式关闭且成功后，将 A 标为已关闭；仅当 A 是当前会话时才清空指针（当前是 B 时关闭 A，当前仍是 B）。忙碌或待审批时保留 A。已关闭的 A 不自动恢复。 |
| 同项目新开 Claude 对话，或原对话切到另一项目 | 使用独立记录；返回原对话、原项目时找回各自的当前会话。 |

**宿主身份。** [Claude Code 官方变更记录](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)与 [Skills 文档](https://code.claude.com/docs/en/skills)记载 `${CLAUDE_SESSION_ID}` 从 `v2.1.9` 起支持 Skill 字符串替换。Gemini Skill 使用宿主展开后的值向桥接器声明对话作用域；启用书签时，空值、未展开的字面量 `"${CLAUDE_SESSION_ID}"` 或无效标识返回 `invalid_client_conversation_id`，不猜测 UUID，也不以桥接器 PID 替代。其他 MCP 客户端未启用书签时，继续按 v0.3.1 的句柄调用，不新增必填参数、不写书签。已绑定作用域的句柄校验归属，调用方传错标识时不读写另一个作用域。

## 2. P0：桥接服务负责书签

桥接服务按对话和项目分文件维护书签（`~/.local/state/acp-session-bridge/scopes/<sha256(clientConversationId + "\0" + projectRoot)>.json`，目录 `0700`，文件 `0600`）。Skill 负责解释用户意图和展示结果，不调用 Bash 或 Python 搬运索引。会话创建、切换、恢复、轮次结算及显式关闭时，由持有该状态的代码更新书签；即使客户端没有再次轮询，已结束的轮次也要在 `consumePrompt` 或 `handleProcessExit` 结算时自动落盘。`list`、`status`、`get_session` 和 `get_events` 只观察状态，不靠查询触发写入。

**内容与迁移。** 只存恢复所需的元数据：归属、当前指针、稳定编号及名称、agent、`projectRoot`、`sessionCwd`、桥接 `sessionId`、下游 `acpSessionId`、持有权租约 `(ownerId, ownerEpoch)`、已核实的配置、最近一轮 `promptId`、游标和状态。**严禁存储问题、回答、源码、事件正文或凭据**（物理杜绝桥接器自行重放旧提问文本）。文件原子替换（同目录 `<file>.tmp.<pid>.<seq>` → `fsync` → `rename`），失败时保留上一份有效记录。升级采用**按作用域懒迁移**：新分片缺失且旧 `~/.local/state/acp-session-bridge/gemini-sessions.json` 中有明确匹配项时，只读查询仅在内存中解析旧记录合并展示；首次需要持久状态的写操作才创建新分片文件，保留旧单文件原样、A/B 编号、当前指针、下游 ID 和已关闭状态。记录损坏或归属不清时报告原因，不以空文件覆盖。

**发送前和回答后，写入失败有不同处理（含 `prompt` 与带初始问题的 `start_session` 等所有实际触发下游 `session/prompt` 的入口）：**

| 时点 | 桥接服务和 Skill 的行为 |
| --- | --- |
| 即将发送新一轮业务提问 | 先在 `<scope>.lock` 内校验当前句柄的 `(ownerId, ownerEpoch)` 仍为磁盘最新持有者，分配本轮 `promptId` 并持久记录 `state: "pending_send"`（若带未知结果确认，则在同一次锁内原子消费 `P_old` 并写入 `P_new = pending_send`），写盘成功后才调用下游 `driver.prompt`。若写盘失败或持有权已失配，明确报错/提示“问题未发送，书签未保存”；下游 `session/prompt` 调用次数为零。 |
| 发送后桥接进程崩溃，磁盘只有 `pending_send`、`running` 或 `cancel_requested` 记录 | 下一次先检查本进程内存活句柄与墓碑。若跨进程重启导致内存无记录，即使部分协议（如 ACP v2 `session/resume`）支持事件回放，只要无法把下游终态可靠关联到原桥接 `promptId`，一律判定为 `outcome_unknown`（结果未知），不依据更早一轮的 `completed` 自动续发。 |
| 下游已完成，最终状态写入失败 | 仍返回原 `promptId`、终态和完整回答，附 `bookmarkPersistence: { saved: false, errorCode }`；Skill 提示“本轮已完成，书签未保存”。保留本进程内存中的终态（活句柄或墓碑）；同进程后续追问直接采信内存终态并补写磁盘，不重发原问题。书签告警与业务错误分别呈现，不返回含私人路径的原始异常。 |

**多进程归属与异常接管（排他执行权 + Fencing Token）：**
1. **启动子进程前原子预占恢复权**：两个终端同时恢复同一个 Claude 对话的会话 A 时，桥接器先通过同目录排他短锁 `<scope>.lock`（`O_CREAT | O_EXCL`，内记持锁进程标识与获取时间；若持锁进程被杀且锁已超短锁上限，后续进程核实持锁者已死后可安全清理陈旧短锁）进入临界区。先获锁的一方验证 A 无活跃持有者后，在启动下游子进程**之前**，取得会话 A 的排他执行权，将书签中 A 的租约更新为 `{ ownerId: instanceUuid, ownerEpoch: prevEpoch + 1, status: "resuming", bridgePid, updatedAt }` 并原子写盘。另一终端读到活跃持有者后，**在启动任何子进程前立即退出并报告占用**，保证下游 `session/load` 调用总数严格为 1。
2. **Fencing Token 拦截旧持有者迟到写入与发题**：每个内存 `ManagedSession` 绑定获取持有权时的 `(ownerId, ownerEpoch)`。所有发送前 `pending_send` 写盘、后台轮次结算、退出回调或配置更新写盘时，必须在 `<scope>.lock` 内校验磁盘上该会话的 `lease.ownerEpoch === session.ownerEpoch && lease.ownerId === session.ownerId`。不匹配时不仅直接丢弃迟到写入，若旧进程正准备发起新一轮 `driver.prompt`，也会因 `pending_send` 校验失败而立即中止发送并关闭本地过期句柄。后台轮次结算仅按字段合并更新 `sessions[label]`，绝不覆写顶层 `currentLabel`。
3. **旧持有者休眠醒来与 `SIGKILL` 后的安全接管边界**：PID 仅用于诊断展示，不单凭 `kill(pid, 0)` 判定身份；**心跳过期只触发核查，不单独授权接管**。只有取得排他执行权（如旧进程持有的内核级会话锁已随进程终止由 OS 释放）、**确认旧执行者不能继续操作 A** 时，才允许新进程接管：
   - 若旧进程仅因机器休眠或 `SIGSTOP` 暂停而停止心跳，但其进程与排他锁仍未释放，新进程 P2 必须报告占用，防止 P1 醒来后通过原有 `agy` 管道与 P2 并发向 A 发题；
   - 若确认旧执行者已终止：当书签中 `lastPrompt.state` 为 `completed`、`cancelled` 或无历史提问（**空闲终态**）时，新桥接进程直接递增 `ownerEpoch` 安全接管并调用 `load_session`；当书签中 `lastPrompt.state` 为 `pending_send`、`running` 或 `cancel_requested`（**非终态**）时，将状态标记为 `outcome_unknown` 并阻断自动发题。

## 3. P0：普通追问自动恢复

`/gemini <追问>` 和 `/gemini use A` 使用相同的身份与配置校验规则。桥接器重启后桥接句柄可以变化；恢复成功要求仍是原 agent、原 `sessionCwd` 和原下游 `acpSessionId` 对应的讨论。

1. **找活句柄。** 核对作用域和下游身份；若已在运行或待审批，返回原 `promptId` 及实时状态，不新增提问。若当前指针缺失且有多个候选，列出供选择，不猜测。
2. **恢复离线会话与游标重置。** 有旧记录、未显式关闭且可安全恢复时，先原子取得排他恢复权 `ownerEpoch`，再以书签中的原 `sessionCwd` 和 `acpSessionId` 调用 `load_session`。由于新桥接句柄的事件序号 `nextSequence` 从 `1` 重新开始（[`manager.ts:706`](https://github.com/ummmme/acp-session-bridge/blob/9837730/src/sessions/manager.ts#L703-L707)），恢复绑定成功后必须将书签中的事件读取游标重置为新句柄的起始游标（`0`），防止旧大序号游标跳过新句柄的首批事件。下游不支持恢复、历史已不存在、旧执行者仍可能存活时，分别报告，保留旧记录和当前指针。
3. **在有界等待窗口内按四步顺序验证有效配置（兼容模型目录与思考档位分批到达）：**
   - **第一步（策略预检与持续等待目标型号出现）**：若存在期望型号 `expectedModel`，先检查其是否被当前静态策略（`allowedModels` / `deniedModels`）明确禁止——若策略禁止则立即失败；否则在有界等待窗口（`DEFAULT_ASYNC_CONFIG_OPTION_TIMEOUT_MS`）内调用 `waitForConfigOptions` **持续等待 `discoverAdvertisedModels` 结果中出现 `expectedModel` 且模型项具有 `currentValue`**（若第一批模型目录只公布 `flash`、第二批才公布 `pro`，在窗口期内继续等待而非在第一批立即判败；窗口到期仍未看到 `expectedModel` 才报告“未能核实原型号”）。模型出现后，若 `currentValue !== expectedModel`，调用 `setConfigOption` 切至 `expectedModel` 并读回确认。
   - **第二步（在目标型号已生效后，等待包含精确目标值的思考档位/附属配置）**：若书签记录了原先选定的思考档位（无论是 `thinkingEffort` 策略映射值还是 `local-agy` 的原始 `config[thoughtConfigId]`），在**第一步切完目标型号之后**，在剩余有界窗口内等待对应配置项出现**且其 `options` 枚举中已包含该精确目标值**（分批推送时若第一批仅含 `["low"]` 则继续等待；**恢复核验严禁调用 `resolveThinkingEffort` 向下取整静默降级为 `low`**）。若原先未选定档位，则不凭空指定。
   - **第三步（按需修正被重置的思考档位）**：若下游在恢复或第一步切换型号时将思考档位重置为默认值（`currentValue !== expectedThinkingValue`），调用 `setConfigOption` 修正为 `expectedThinkingValue`。
   - **第四步（全量最终读回断言）**：对最新 `configOptions` 一次性同时断言 `model.currentValue === expectedModel` 且 `thinking.currentValue === expectedThinkingValue`；两项都读回一致后才更新书签绑定、允许发送。任一步骤不匹配或超时，关闭临时会话、释放名额与恢复权，保留旧书签，业务提问数为零。
4. **决定是否发送、取消两阶段确认与未知结果原子消费：**
   - **取消两阶段拆分**：[现有 `cancelPrompt`](https://github.com/ummmme/acp-session-bridge/blob/9837730/src/sessions/manager.ts#L923-L949) 发出 `session/cancel` 时，仅记为 **`cancel_requested`**（此时若 5 秒等待超时返回，`consumePrompt` 尚未退出，`promptActive` 仍为 `true`）；必须等到 `consumePrompt` 收到下游停止确认并退出（`promptActive = false`）后，才结算落盘为终态 **`cancelled`**。`cancel_requested` 期间禁止发新提问。
   - **未知结果单次原子确认握手**：当上一轮处于 `outcome_unknown`（关联 `interruptedPromptId: P_old`）时，保留 A 和 `P_old`，普通追问一律拒绝。用户在核对工作区后若明确要求“继续 A，发送这条新追问”，调用 `prompt` 时必须显式传入匹配的 `acknowledgeUnknownOutcomeForPromptId: P_old`（且会话已通过归属和上述四步配置检查）。服务端**必须在同一次受 `<scope>.lock` 与 `ownerEpoch` 保护的书签写入中，原子完成“核对并消费 `P_old` + 分配 `P_new` + 将当前轮次写为 `P_new (pending_send)`”**，写盘成功后才向下游发送本次新追问。这保证了：① 两个并发请求同时确认同一 `P_old` 时，只有一个能消费成功并发题；② 写完 `P_new = pending_send` 后若立刻崩溃，重启后 `lastPrompt.id` 已是 `P_new`，再次提交旧 `P_old` 确认也不会重放。
   - 收到 401、429 等错误要结合实际发生阶段（配置期 / 发送前 / 发送后），已确认结束的截断、拒答或取消按各自真实终态报告，不伪装成完整回答。

## 4. P1：按主题管理会话与接口最小集

保留 A/B/C 稳定编号，不强制命名。`/gemini rename 安装体验` 重命名当前会话；`/gemini rename A 安装体验` 重命名指定会话。自定义名称不得占用纯大写字母编号（`^[A-Z]+$`）或保留子命令 `new`、`list`、`use`、`close`、`status`、`rename`、`config`。重名、冲突或目标不存在时提示原因，不改变当前指针。

| 交互 | 预期行为 |
| --- | --- |
| `/gemini use 安装体验`、`/gemini close 安装体验` | 名称与编号定位同一条记录。按名称关闭仍保留忙碌保护。 |
| `/gemini list` | 展示稳定编号、名称、当前标记及状态。每轮回答也在现有会话标识中带出名称，例如 `B · 权限设计`。 |
| `/gemini status` | 只读展示当前会话、最近核实的配置、最近一轮状态和待审批情况。离线时注明哪些值来自书签。 |

`list` 和 `status` 不新建、不恢复会话，不发送模型请求。

**MCP 接口最小集分层（兼容无书签客户端）：**

| 工具类别 | 涉及工具 | 新增可选参数与书签职责边界 |
| --- | --- | --- |
| **作用域创建与恢复** | `start_session`<br>`load_session` | 可选接收 `clientConversationId`、`projectRoot`、`sessionName`（仅 `start`）、`target`（仅 `load`，编号或名称，省略取 `current`），`load_session` 增补可选期望配置 `model` / `thinkingEffort` / `config`。传入 `clientConversationId` 时在服务端内部完成 `projectRoot` 解析、排他恢复权 `ownerEpoch` 预占、原 `sessionCwd` 恢复、有界窗口四步配置核验、事件游标重置与书签绑定更新；若 `start_session` 携带初始 `prompt`，同样走发送前 `pending_send` 写盘保护；不传 `clientConversationId` 时完全保持 v0.3.1 行为。 |
| **业务提问** | `prompt` | 可选接收 `clientConversationId`、`acknowledgeUnknownOutcomeForPromptId`。校验句柄作用域归属与上一轮终态准入；发送前在 `<scope>.lock` 内校验 `ownerEpoch`、原子消费 `P_old`（若有）并落盘 `P_new = pending_send`，写盘成功才调 `driver.prompt`；`consumePrompt` / `handleProcessExit` 结束时后台带 `ownerEpoch` 自动结算落盘。 |
| **显式关闭与管理** | `close_session`（及重命名/切换操作） | 可选接收 `clientConversationId`、`cwd`、`target`（编号或名称）。`close_session(ifIdle: true)` 成功后将书签中该记录标为 `closed`，**仅当被关闭会话正是当前会话时才清空 `current` 指针**；重命名与指向已有活句柄的 `use` 仅原子更新书签元数据，不启动子进程。 |
| **纯只读观测** | `list_sessions`<br>`get_session`<br>`get_events` | 可选接收 `clientConversationId`、`cwd`、`target`。**严格零写盘副作用**：内存中只读合并活句柄、墓碑与分片书签（或内存中只读解析未迁移的旧 `gemini-sessions.json`），返回 `source: "live" \| "tombstone" \| "bookmark"`。 |
| **纯句柄内操作** | `resolve_permission`<br>`cancel_prompt`<br>`set_config_option`<br>`set_mode` | 仅使用已绑定的 `sessionId`。`set_config_option` 成功后、`cancel_prompt` 在 `consumePrompt` 真正退出后，由服务端通过 `session` 内存关联的 `(scopeKey, label, ownerEpoch)` 自动同步书签。 |

## 5. 发布验收

身份和跨天续聊用真实 Claude Code、隔离 Skill 和合成代号验证。并发、崩溃、磁盘故障和分批配置使用可控测试助手，记录下游 `session/load`、`session/prompt` 的实际次数。

| 场景 | 操作与通过标准 |
| --- | --- |
| 宿主身份与双向目录解析 | ① 原对话与 `--resume` 恢复原对话取到相同标识，新对话取得不同标识；分别记录 `--continue`、`--fork-session`、`/clear` 的实测结果和宿主版本。② 根目录建 A 后进入子目录追问命中 A；**反向在子目录 `/repo/sub` 首次建 A（记录 `sessionCwd = /repo/sub`, `projectRoot = /repo`）→ 重启后回到根目录 `/repo` 追问，断言找到同一 A 且传给下游 `session/load` 的 `cwd` 仍为 `/repo/sub`**。③ **同一仓库的两个独立 `git worktree` 各自解析为独立 `projectRoot`，互不串书签**；**仅有用户级 `~/.acp-mcp.json` 时，`~/项目甲` 与 `~/项目乙` 两个非 Git 目录绝不共用书签**。 |
| 正常退出后接回 B 与非当前关闭 | 给 A、B 各一个随机代号，最后选中 B。正常退出 Claude Code，再 `--resume` 并直接追问；下游输入不含答案。B 返回自己的代号且下游 ID 不变，恢复后新句柄事件读取游标已重置，不漏读新句柄首批事件；切回 A 仍可取回 A 的代号。当前为 B 时执行 `/gemini close A`，当前指针仍为 B；显式关闭 B 成功后指针清空且不自动恢复。 |
| 双进程并发恢复、旧进程休眠醒来与破锁接管 | ① 用同步屏障让两个桥接器同时尝试恢复 A：只有一个取得恢复权（`ownerEpoch` 递增），下游 `session/load` 总数为 1，另一方在 spawn 子进程前立即报告占用。② **P1 持有 A 期间被暂停（如 `SIGSTOP` 或模拟休眠停止心跳但未释放排他执行权），P2 尝试接管时报告占用；即使模拟 P1 持有旧 `ownerEpoch` 醒来尝试发题，也在发送前校验中被拦截，绝不出现两个执行者向 A 发题**。③ 随后切换至 B，旧进程迟到的后台结算因 `ownerEpoch` 不匹配被丢弃，不回退当前指针、不覆盖新持有者状态。④ **进程在持有短锁 `<scope>.lock` 或持有空闲会话 A（`lastPrompt.state = "completed"`）时被 `SIGKILL` 强杀且模拟旧 PID 被复用后，后续进程不会永久卡在短锁上，且能安全接管并恢复 A**。 |
| 模型目录与思考档位分批到达及重置防护 | ① **模型目录分批到达：第一批仅公布 `flash`，第二批才公布原书签型号 `pro`，断言在有界窗口内等待到 `pro` 出现后成功恢复**。② 模拟初始恢复型号为 `flash`（档位为 `high`），服务端切回书签型号 `pro` 触发下游将档位重置为 `low`，断言服务端在切完型号后二次等待并将档位修正回 `high`。③ 模拟思考档位候选列表分两批推送（第一批仅含 `["low"]`，第二批含 `["low", "high"]`），断言恢复核验不会在第一批到达时通过 `resolveThinkingEffort` 静默降级为 `low`。以上情况在读回 `pro` + `high` 前业务提问均为 0，核实后本次追问恰好发 1 次。 |
| 原型号被禁或始终缺失 | ① 原型号被当前策略明确禁止时立即失败。② 下游在有界等待窗口结束时仍仅提供型号 B（原型号 A 始终缺失）：报告“未能核实原型号”，临时子进程关闭、名额与恢复权释放、旧书签保留，不自动换型号；业务提问为 0。 |
| 发送与写盘故障 | ① 发送前 `pending_send` 写入失败（含 `prompt` 与带初始问题的 `start_session`）：下游提问为 0。② `pending_send` 写好后、发送前崩溃：重启后判定为 `outcome_unknown`，不自动发送。③ 已发送且回答完成，结算写盘失败：调用方仍收到完整答案和 `bookmarkPersistence.saved: false` 告警；同进程后续追问采信内存终态并补写磁盘；若在写盘失败后进程又崩溃重启，只读到 `pending_send` 记录时报告结果未知，不重复执行。 |
| 忙碌、取消未确认与未知结果并发/崩溃确认 | ① 活任务或待审批返回原 `promptId`。② `cancel_prompt` 发出后下游在 5 秒内未退出（处于 `cancel_requested`、`promptActive = true`）时，拒绝发送新提问，直至下游确认结束才落盘 `cancelled`。③ 当会话处于 `outcome_unknown`（关联 `P_old`）时，不带 `acknowledgeUnknownOutcomeForPromptId: P_old` 的普通追问每次均被拦截（下游提问为 0）。④ **两个并发请求同时确认同一 `P_old` 时，因消费 `P_old` 与写入 `P_new = pending_send` 在同一锁内原子完成，最多一个请求成功发题（下游提问总数为 1）；写入 `P_new = pending_send` 后立刻崩溃，重启后再次提交旧 `P_old` 确认也会被拒绝，绝不重放**。⑤ 空闲退出且上一轮已核实完成的 A 仍可正常恢复。 |
| 升级与旧命令兼容 | 各作用域首次写操作懒迁移后保留 A/B、当前指针、已关闭状态和下游 ID；旧文件内容不变。按名称与按编号定位一致；`list`、`status` 纯内存读取不落盘、不联系模型。不启用书签的客户端沿用 v0.3.1 行为。 |

## 6. 版本边界

继续采用 stdio 桥接，MCP 服务与 `acp-mcp`、`gemini` 两份 Skill 配套交付。每个桥接进程默认 20 个会话，无自动淘汰。

本版不做跨 Claude 对话共享会话池、脱离宿主运行的常驻服务、对话正文落盘、评审材料预览或多模型自动路由。异构 agent 的 `modelConfigId` 识别可独立评估，继续保持仅可信配置可写。
