### 1.2 跨进程排他执行权、旧进程/孤儿 `agy` 防护与短写锁回收（收敛规则 2）
- **核验状态：【已验证】**
- **代码证据：**
  - [src/runtime/execution_lease.ts](../src/runtime/execution_lease.ts#L47-L199) 与 [src/runtime/node_process.ts](../src/runtime/node_process.ts#L95-L112)：会话执行权（`purpose: "execution"`）在 `127.0.0.1` 绑定确定性独占端口，POSIX 将监听 `fd` 通过 `stdio[3]` 传给下游 ACP 子进程继承并以 `detached: true` 建立独立进程组；Windows 在通过目录删除探针后使用带 `_O_TEMPORARY`（最后句柄关闭即由系统删除）的 `.exec` 文件句柄传给 `stdio[3]`。
  - [src/bookmarks/scoped_sessions.ts](../src/bookmarks/scoped_sessions.ts#L95-L111) 与 [L244-L261](../src/bookmarks/scoped_sessions.ts#L244-L261)：子进程启动后在 `beforeInitialize` 同步将 `childPid` 写入书签；新进程接管时除获取 `ExecutionLease` 外，还通过 `canRecover` 执行 `process.kill(-e.childPid, 0)` 确认原进程组已退出（`ESRCH`），防止子进程主动关闭 `fd 3` 后仍在后台运行。
  - [src/bookmarks/store.ts](../src/bookmarks/store.ts#L149-L200)：短写锁（`purpose: "transaction"`）使用独立端口段做 `[0, 5, 15, 30, 60, 100, 200]ms` 有界退避，获锁后通过 `link(tmp, path)` 原子发布 `acp-scope-lock-v1:<key>:<pid>:<ts>` 锁文件。前序写进程崩溃后内核自动释放事务端口，后继获锁者核对同协议前缀后安全回收残留 `.lock`；对格式不明的外部锁文件保持原件并报 `scope_busy`。
- **测试覆盖：**
  - [tests/execution_lease.test.ts](../tests/execution_lease.test.ts#L96-L154)（验证 `SIGSTOP` 暂停 P1、P1 被 `SIGKILL` 但子进程仍存活、子进程退出后双进程竞争仅 1 个获锁）。
  - [tests/scoped_stdio.test.ts](../tests/scoped_stdio.test.ts#L198-L232)（端到端验证桥接进程 `SIGSTOP`、`SIGKILL` 留孤儿 ACP 进程期间新桥接器 0 次 `session/load`，孤儿进程退出后并发恢复仅 1 次 `session/load`）。
  - [tests/bookmark_store.test.ts](../tests/bookmark_store.test.ts#L182-L205)（未知外部锁保留 vs 写事务崩溃残留锁自动回收）。

## 2. 建议在打 `v0.4.0` 发布标签前收口的 3 项细节

### 2.1 同进程子进程刚退出、后台 `retireSession` 尚未跑完时的 `load_session` 竞态窗口
- **触发条件 → 后果：**
  当绑定了书签的子进程意外退出时，[src/sessions/manager.ts:1574-1612](../src/sessions/manager.ts#L1574-L1612) 的 `handleProcessExit` 同步设置 `session.processExit = exit`，随后异步调用 `void this.retireSession(session)`。
  在 [src/sessions/manager.ts:1707-1722](../src/sessions/manager.ts#L1707-L1722) 中，绑定了 `session.journal` 的会话必须先 `await session.prompt.done` 并 `await this.runRetirementCallback(session)`（写盘将书签改为 `offline` 并释放 `lease`），**之后**才在第 1713 行执行 `this.sessions.delete(session.id)`。
  若调用方在子进程刚退出、`runRetirementCallback` 写盘尚未完成的数毫秒窗口内调用 `load_session`：
  - 此时磁盘书签 `entry.status` 仍为 `"live"`，且 `manager.hasSession(entry.sessionId)` 仍为 `true`；
  - [src/mcp/server.ts:1458-1496](../src/mcp/server.ts#L1458-L1496) 会误入 `reused: true` 分支，把一个 `processExit` 已非空、1ms 后就会被删除转入墓碑的失效 `sessionId` 当作活句柄返回给调用方。
- **最小修复：**
  1. 在 `SessionManager` 上提供 `awaitRetirementIfExiting(id: string): Promise<void>`（当 `this.sessions.get(id)?.retirementTask` 或 `processExit` 存在时，先 `await session.retirementTask`）；
  2. 在 [src/mcp/server.ts:1440](../src/mcp/server.ts#L1440) 的 `load_session`（以及 `scoped.observe` / `list_sessions`）中，若 `entry.sessionId` 对应的本进程会话已存在 `processExit` 或 `retirementTask`，先等待 `retirementTask` 完成（使书签落盘为 `offline`、旧句柄转入墓碑且释放 `ExecutionLease`），然后再走正常的 `reserveLoad` 离线恢复分支（且在 [src/mcp/server.ts:1465](../src/mcp/server.ts#L1465) 增加 `!live.processExit` 守卫）。

### 2.2 同进程终态结算写盘失败后，`observe` / `list_sessions` / `load_session(reused)` 的 `lastPrompt` 应优先取内存已结算终态
- **触发条件 → 后果：**
  当同一桥接进程内某一轮回答已正常完成（内存 `prompt.terminal === "completed"`），但因临时锁冲突或磁盘故障导致终态写盘失败（`bookmarkPersistence.saved === false`，磁盘书签上的 `entry.lastPrompt.state` 仍停留在 `"running"` 或 `"pending_send"`）时：
  - 虽然直接调用 `prompt` 会在 [src/sessions/manager.ts:358-367](../src/sessions/manager.ts#L358-L367) 自动根据内存 `previous.terminal` 补写修复磁盘书签；
  - 但按照 [.agents/skills/gemini/SKILL.md:34](../.agents/skills/gemini/SKILL.md#L34)，普通 `/gemini <question>` 在发 `prompt` 前会先调 `list_sessions` 和 `load_session`。目前 [src/mcp/scoped_bindings.ts:70](../src/mcp/scoped_bindings.ts#L70)、[src/mcp/server.ts:1491](../src/mcp/server.ts#L1491) 与 [src/mcp/server.ts:2019](../src/mcp/server.ts#L2019) 均直接返回磁盘上的 `entry.lastPrompt`（即落后的 `"running"`），与同响应中的 `promptActive: false` / `status: "idle"` 矛盾，可能导致调用方误以为上一轮仍在运行。
- **最小修复：**
  在 `SessionSnapshot.prompt`（[src/sessions/manager.ts:452-465](../src/sessions/manager.ts#L452-L465)）中暴露内存已计算的 `terminal?: TurnState`（或 `cancelRequested?: boolean`）。当 `scoped.observe`、`list_sessions` 和 `load_session(reused: true)` 命中本进程持有的 `live` 快照且 `live.prompt` 存在时，`lastPrompt` 优先取内存真值（如 `live.prompt.terminal ? { promptId: live.prompt.id, state: live.prompt.terminal } : entry.lastPrompt`）。
