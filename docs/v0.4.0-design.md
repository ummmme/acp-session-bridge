# v0.4.0 技术设计：一次追问如何回到原会话

**【开发中】** 基线 `v0.3.1`（`9837730`）。[需求与发布验收](./v0.4.0-requirements.md)。本稿给实现和测试使用；书签功能按作用域显式启用，旧客户端的调用不创建状态文件。

## 身份与目录

Claude Code 负责展开 `${CLAUDE_SESSION_ID}`。在 Claude Code 2.1.296 的隔离 Skill 测试中，直接检查发送给本地模拟端点的模板展开文本：原对话与 `--resume` 一致，新对话和 `--fork-session` 得到不同 ID，`--continue` 延续刚才的对话。交互式 `/clear` 的隔离测试停在宿主的工作区信任提示，仍需人工验收。桥接器接受校验过的宿主标识，不从进程环境、PID 或对话记录推断。

`resolveConversationScope` 将真实工作目录记为 `sessionCwd`。先向上查最近的 `.git` 目录或文件；找不到才采用最近的项目级 `.acp-mcp.json`，排除用户级配置。没有标记时按已验证的宿主项目根、启动根、当前真实目录依次回退。显式根必须是当前目录的真实祖先。`projectRoot` 与宿主标识共同生成分片键，`sessionCwd` 在创建下游会话时固定。切回会话或恢复时使用书签中的原工作目录。

## 从提问到结算

| 时点 | 桥接器操作 | 失败行为 |
| --- | --- | --- |
| 从 A 或 B 中选中目标 | 核对归属；查本进程活句柄和退出记录。需要恢复时先取得该会话的排他执行权，再启动下游。 | 其他执行者仍能操作该会话时，报告占用，不启动第二个进程。 |
| 恢复配置 | `load_session` 精确核实原模型，再核实该模型对应的原档位。显式禁用的型号立即失败，分批到达的选项在同一截止时间内等待。 | 配置不符、超时或无法核实时，释放本次临时句柄，不发送问题，不替换当前书签。 |
| 预留新一轮 | 在同一个书签事务中重读 A、校验持有者和上一轮状态，然后写入新的 `promptId` 与 `pending_send`。显式确认未知轮次时，在该事务中消费原 `promptId`。 | 写入未确认或持有者已变更时，不调用下游 `session/prompt`。 |
| 发送及结算 | 在仍持有会话执行权期间调用下游。只有匹配同一持有者、同一 `promptId` 的回调才能更新 A 的状态；回调不调整项目的当前指针。 | 已得到模型回答但结算写盘失败时，保留原答案，附脱敏保存告警。若随后重启，只能读到待定记录时，报告结果未知，不重放。 |

恢复时，旧轮的 `pending_send`、`running` 和 `cancel_requested` 归为 `outcome_unknown`，除非已有可关联的确切终态。用户确认 `P_old` 时，新轮使用 `P_new`；两个请求竞争同一确认，最多一个完成预留。新桥接句柄从游标 0 开始读。正常退出保留离线书签；显式关闭成功才写 `closed`。

## 短写锁与会话执行权

**短写锁保护 JSON 文件；会话执行权保护下游进程。** 对本地 JSON 更新使用排他创建短锁、重新读盘、按字段修改、同目录临时文件写入并同步，再原子替换。POSIX 上同步目录并检查目录和文件权限。只读查询不建目录、不创建锁。遇损坏记录或来源不明的锁时保留原件。

跨进程执行权必须从预占一直保持到下游停止操作 A。不能只在 `pending_send` 写入时比一次 `ownerEpoch`：P1 可能在写完书签、尚未发送时被暂停。P2 在 P1 仍持执行权时必须拒绝接管；P1 正常恢复时仍可继续。真正移交后，旧回调也必须因 `(ownerId, ownerEpoch)` 不匹配而失效。

桥接器在分片事务内为每条记录取得独占的本机回环监听端口。POSIX 通过 `stdio[3]` 把描述符传给 ACP 子进程；桥接器在发送第一条 ACP 请求前同步保存子进程组号。接管方须先取得端口，再核实原进程组已退出。端口冲突、权限不足或进程组号已复用时报告占用。Windows 使用“最后一份句柄关闭时由系统删除”的独占文件，经本地文件系统探测后将句柄传给助手。直连 `agy.exe acp` 在桥接器异常退出后同时核对端口、文件租约和原子进程退出；未知启动链保留占用记录。正常退出写 `offline`。Windows 分支待原生环境验收。

短事务使用另一段回环端口串行创建和回收 `<scope>.lock`。持有者通过硬链接一次公布完整锁标记，写完后先清除标记再释放端口。新的持有者取得端口后可回收相同协议、相同键的残留锁；遇到未知标记保留原件。

## 实现与验收

`ScopedSessions` 维护分片、执行权和当前指针；`SessionManager` 在发送和结算时更新轮次。两份 Skill 使用 MCP 接口，普通 `/gemini` 根据宿主展开的对话标识读取书签。`list` 和 `status` 只读，`rename` 和离线 `close` 只更新元数据。旧索引由服务只读解析，首次修改写入独立分片，原文件保留。

- `tests/scoped_stdio.test.ts` 启动独立 MCP 进程和可控 ACP 助手：在子目录创建 A、B，从根目录恢复 B，取回两个不同代号，验证非当前关闭、暂停、强杀和旧助手退出后的接管。
- `tests/claude_scoped_resume.test.ts` 使用已安装的 Claude Code、隔离项目 Skill、真正的打包入口和本地合成模型端点。运行 `npm run build` 后设置 `ACP_TEST_CLAUDE_CLI` 为宿主绝对路径可单独复验；不需要提供方凭据。
- 发行前仍需验证目标平台产物、交互式 `/clear`，以及真实 `agy` 账户下的恢复表现。以上两项集成测试均使用可控 ACP 助手。

## 第二批接入前已对齐的 4 项收敛规则

1. **思考档位持久化“已读回的配置项与值 `{ configId, value }`”（`src/bookmarks/store.ts` 与 `src/models/resume_verification.ts`）**：
   - 标准 `local-agy` 不配置 `models.thinkingEffort` 映射表，其思考档位来自下游原始 `configOptions`（如 `thought_level = "high"`）。
   - 书签保存已从下游实际读回的 `{ configId, value }`（若用户当初通过标准化的 `thinkingEffort` 选型，可另外保留该偏好）。恢复时无需依赖本地映射表即可按 `{ [configId]: value }` 精确核验。
   - **验收**：使用未配置 `thinkingEffort` 映射表的 `local-agy` 夹具，恢复后精确读回 `thought_level = "high"`。
2. **短写锁有界退避与覆盖“旧子进程仍存活”的会话执行权验收门槛（`src/bookmarks/store.ts` 与运行时）**：
   - **短写锁有界退避**：`store.update` 获取 `<scope>.lock` 遇到 `EEXIST` 时先做毫秒级有界退避重试，吸收同分片并发写冲突；对归属不明的锁保留原件并报告 `scope_busy`。
   - **会话执行权必须覆盖下游子进程生命周期**：仅跟踪桥接进程 P1 不足以证明旧 `agy` 已停止（P1 被 `SIGKILL` 强杀后，旧 `agy` 子进程可能继续存活，见 `tests/server_lifecycle.test.ts:261`）。执行权句柄（如让下游子进程通过 `stdio[3]` 继承的排他锁文件描述符/管道句柄）需由 **P1 与其启动的下游 `agy` 子进程共同持有**，且所有执行权探测、清理与重建必须在持有 `<scope>.lock` 的临界区内串行执行（杜绝竞争者并发误删对方刚建立的端点）。只要 P1 或旧 `agy` 任一存活，内核句柄即未释放。
   - **三场景接管验收门槛（跑通前保留“归属不明即报告占用”）**：① P1 被暂停（`SIGSTOP`）时，P2 不启动第二个 `agy`；② P1 被 `SIGKILL` 强杀而旧 `agy` 仍存活时，P2 不调用 `session/load`；③ 确认 P1 与旧 `agy` 均已退出后，P2 才恢复一次。
3. **模型恢复与 JSON 字段顺序解耦，并用实际读回值更新状态（`src/models/resume_verification.ts` 与 `src/mcp/server.ts`）**：
   - 无论目标型号来自顶层 `model` 还是 `config`（如 `{ thought_level: "high", model: "pro" }`），先统一提取并解析目标型号，再按“切模型 → 等档位 → 读回两项”顺序执行，最后用实际读回结果更新 `manager.recordModelSelection` 和书签。
   - **验收**：交换 `config` 中 `thought_level` 与 `model` 两个 JSON 键的顺序，两次均恢复为 `pro` / `high`，核实前业务提问数均为 0。
4. **下游明确返回失败使用独立终态 `failed_confirmed`，与 `not_sent`、`outcome_unknown` 严格三分（`src/bookmarks/turn.ts`）**：
   - 仅依据发送阶段与协议终态划分，不靠“未观察到工具或审批事件”推断下游未执行动作：
     - `not_sent`：已确认尚未调用下游发送接口；
     - `failed_confirmed`：已发送，且收到与本轮匹配的终结错误响应（报告失败，允许用户发起一条新追问，不自动重发旧题）；
     - `outcome_unknown`：已发送，连接中断或进程退出，缺少可关联的本轮终态（保留原 `promptId`，走未知结果显式确认流程）。
